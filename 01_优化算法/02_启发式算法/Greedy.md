# Greedy：贪心算法

Greedy 指 Greedy Algorithm（贪心算法）。

# 1. 一句话说明它是什么

> 贪心算法是一种每一步都选择“当前看起来最好”的方案，主要用于快速构造一个可行解或在特定问题中找到最优解。

核心思路：
```text
当前选最好的
→ 选完不回头
→ 继续下一步
```

例如安排任务时，可以每次选择：
- 最早结束的任务；
- 距离最近的地点；
- 成本最低的资源；
- 当前利润最高的项目。

注意：

> 当前最好不一定等于最终最好。
只有具有特定结构的问题，贪心才能保证全局最优；其他问题中，它通常只是快速得到一个较好方案。

# 3. 人和算法分别负责什么
```text
现实问题
  ↓
人需要完成的工作
  ├── 定义候选对象
  ├── 定义“当前最好”的评价规则
  ├── 定义可行性检查
  └── 定义停止条件
  ↓
贪心算法需要完成的工作
  ├── 比较当前候选对象
  ├── 选择当前最优对象
  ├── 检查是否可行
  ├── 更新当前状态
  └── 重复直到结束
  ↓
最终结果
  └── 一个完整可行方案
```

人向算法提供：
- 候选对象；
- 贪心规则；
- 约束检查；
- 当前状态；
- 停止条件。

算法返回：
- 选择结果；
- 选择顺序；
- 目标值；
- 是否可行。

# 5. 从抽象现实问题中提取模型的方法

```text
每一步需要选择什么？
→ 候选对象

什么叫“当前最好”？
→ 贪心规则

什么情况不能选择？
→ 可行性约束

选择后哪些信息会变化？
→ 当前状态

什么时候停止？
→ 终止条件
```

常见自然语言：

| 现实描述 | 对应内容 |
|---|---|
| 每次选最近的 | 距离最小规则 |
| 优先处理最早到期的 | 截止时间规则 |
| 优先选择收益最高的 | 收益最大规则 |
| 不能超过容量 | 可行性检查 |
| 机器不能发生冲突 | 资源约束 |
| 所有任务都已处理 | 停止条件 |

# 6. 总体输入与输出

| 类型 | 内容 | 示例 |
|---|---|---|
| 原始业务输入 | 现实问题数据 | 任务、时间、成本 |
| 算法输入 | 候选集合和贪心规则 | 优先选择最早结束任务 |
| 内部数据 | 当前状态和剩余候选 | 当前结束时间、未选任务 |
| 输出 | 完整选择结果 | 被安排的任务序列 |

# 7. 完整运行流程

```text
现实问题
  ↓
整理候选对象
  ↓
定义贪心规则
  ↓
初始化当前状态
  ↓
选择当前最好候选
  ↓
检查是否可行
  ├── 可行：加入结果并更新状态
  └── 不可行：跳过
  ↓
判断是否结束
  ↓
输出方案
```

# 9. 每个模块的输入、输出和构成
## 9.1 问题数据 Problem Data
### 作用
保存候选对象和已知数据。

### 输入
- 任务；
- 成本；
- 时间；
- 容量；
- 资源信息。

### 内部构成
```text
ProblemData
├── Candidates
├── Parameters
└── Constraints
```

### 处理过程
读取并整理候选对象。
### 输出
- 候选集合；
- 约束数据。

### 是否需要用户自己实现
通常需要自己实现。

## 9.2 贪心规则 Greedy Rule
### 作用
判断当前应该优先选择哪个候选对象。
### 输入
- 当前候选集合；
- 当前状态。

### 内部构成
```text
GreedyRule
├── Score
└── Priority
```

### 处理过程
1. 为候选对象计算优先级；
2. 找出当前最优对象。

### 输出

- 当前最优候选对象。

### 是否需要用户自己实现

通常需要自己设计，这是贪心算法最核心的部分。

## 9.3 可行性检查 Feasibility Check

### 作用
检查当前候选对象能否加入方案。
### 输入

- 当前候选；
- 当前方案；
- 约束条件。

### 内部构成
```text
FeasibilityCheck
├── CapacityCheck
├── ConflictCheck
└── RuleCheck
```

### 处理过程
检查加入候选后是否违反约束。

### 输出
```text
可行：True
不可行：False
```

### 是否需要用户自己实现

通常需要自己实现。

## 9.4 状态更新 State Update

### 作用

选择候选对象后更新当前方案。

### 输入

- 已选候选；
- 当前状态。

### 内部构成

```text
StateUpdate
├── AddCandidate
├── UpdateResources
└── RemoveCandidate
```

### 处理过程

1. 将候选加入结果；
2. 更新剩余资源；
3. 从候选集合中删除已处理对象。

### 输出

- 新状态；
- 新候选集合。

### 是否需要用户自己实现

通常需要自己实现。

## 9.5 主求解模块 Solver

### 作用

重复执行选择、检查和更新。

### 输入

- 问题数据；
- 贪心规则。

### 内部构成
```text
Solver
├── Select
├── Check
├── Update
└── Stop
```

### 处理过程

```text
选择
→ 检查
→ 更新
→ 重复
```

### 输出

- 最终方案；
- 目标值。

### 是否需要用户自己实现

通常需要自己实现，但主循环一般很短。

# 11. 用户需要实现什么

## 通常需要自己实现

- 候选对象；
- 贪心规则；
- 可行性检查；
- 状态更新；
- 停止条件；
- 结果验证。

## 通常由标准库提供

- 排序；
- 最小值和最大值查找；
- 优先队列；
- 集合与列表操作。

贪心算法通常不需要专门求解器。

# 12. 它真正帮我解决什么

| 问题 | 回答 |
|---|---|
| 帮助理解问题？ | 不会自动理解，需要人定义选择规则 |
| 帮助建立模型？ | 部分帮助，需要把问题拆成逐步选择 |
| 帮助搜索答案？ | 是，但每步只保留当前选择 |
| 帮助预测结果？ | 不是 |
| 帮助连续决策？ | 可以逐步决策，但通常不学习 |
| 帮助验证可行？ | 可以，通过可行性检查避免明显冲突 |

# 13. 适用与不适用场景

| 比较适合 | 原因 |
|---|---|
| 需要快速方案 | 计算通常很快 |
| 候选可以逐步选择 | 容易构造贪心规则 |
| 大规模问题 | 不需要搜索所有组合 |
| 已证明贪心最优的问题 | 可以得到全局最优解 |
| 其他算法的初始解 | 能快速生成候选方案 |

| 不太适合 | 原因 |
|---|---|
| 当前选择影响很久以后 | 容易选错 |
| 选择后需要反复修改 | 基础贪心通常不回退 |
| 约束高度耦合 | 单步判断可能不够 |
| 必须保证全局最优 | 贪心通常没有保证 |

# 14. 与相近算法比较

| 对比项 | 贪心 | 局部搜索 | 动态规划 |
|---|---|---|---|
| 选择方式 | 每次选当前最好 | 修改已有完整方案 | 保存多个子问题结果 |
| 是否回退 | 通常不回退 | 会反复修改 | 会比较不同状态 |
| 速度 | 通常很快 | 中等 | 取决于状态数量 |
| 全局最优 | 只在特定问题保证 | 通常不保证 | 模型正确时通常可保证 |
| 典型用途 | 快速构造方案 | 改进已有方案 | 有清晰子问题结构的问题 |

# 15. 可以与其他算法融合的位置

## 15.1 贪心＋局部搜索

```text
贪心
  ↓ 快速生成初始方案
局部搜索
  ↓ 调整不好的局部选择
更好的方案
```

贪心负责速度，局部搜索负责修正。

## 15.2 贪心＋GA/NSGA-II

```text
贪心
  ↓ 生成较好的初始个体
GA或NSGA-II
  ↓ 继续进化搜索
最终方案
```

可以减少随机初始化质量太差的问题。

## 15.3 贪心＋MILP/CP

```text
贪心
  ↓ 提供初始可行解
MILP或CP
  ↓ 继续优化或证明最优
精确方案
```

贪心提供热启动，精确求解器继续改进。

## 15.4 贪心＋RL

```text
当前状态
  ↓
RL选择使用哪条贪心规则
  ↓
贪心完成当前选择
```

RL 可以动态选择：

- 最短时间优先；
- 最低成本优先；
- 最早交期优先。

# 16. 最小示例

## 16.1 原始问题

会议室只能同时举办一场会议，希望安排尽可能多的会议。

候选会议：

| 会议 | 开始 | 结束 |
|---|---:|---:|
| A | 1 | 3 |
| B | 2 | 5 |
| C | 4 | 6 |
| D | 6 | 7 |

## 16.2 贪心规则

```text
每次选择结束时间最早且不冲突的会议。
```

## 16.3 执行过程

```text
选择A：1—3
B与A冲突，跳过
选择C：4—6
选择D：6—7
```

## 16.4 输出

```text
安排结果：A、C、D
会议数量：3
```

在这个问题中，“最早结束优先”可以保证选出的会议数量最多。

# 17. 一句话总结

> 人负责定义候选对象、贪心规则和可行性条件；贪心算法负责反复选择当前最好的可行对象；最终输出一个快速构造的完整方案，但不一定是全局最优方案。
