# LP：线性规划

本文中的 LP 指 Linear Programming（线性规划），不是其他领域中的 LP 缩写。

LP 更准确地说是一类优化模型，不是某一个固定算法。模型通常由单纯形法、内点法等求解算法处理。

# 1. 一句话说明它是什么

> LP（线性规划）是一种在资源有限、数量可以连续变化的情况下，寻找成本最低、利润最高或资源利用最优方案的方法。

它常用于决定：

- 每种产品生产多少；
- 每个地区运输多少货物；
- 不同资源如何分配；
- 不同原料如何配比；
- 不同投资方向投入多少资金；
- 不同能源来源分别使用多少。

LP 最明显的特点是：

> 变量、约束和目标之间必须是线性关系，而且变量通常允许取小数。

例如：

```text
生产2.5吨产品
运输17.8吨货物
投入35.6万元
使用4.2小时机器时间
```

这些连续数量适合用 LP 表示。

# 3. 人和 LP 分别负责什么

```text
现实问题
  ↓
人需要完成的工作
  ├── 整理已知数据
  ├── 找出需要决定的数量
  ├── 判断这些数量是否允许取小数
  ├── 把资源限制写成线性约束
  ├── 把利润、成本或时间写成线性目标
  └── 检查模型是否符合现实
  ↓
LP求解器需要完成的工作
  ├── 读取变量、约束和目标
  ├── 检查并简化模型
  ├── 确定可行方案的范围
  ├── 在可行范围内搜索更优方案
  ├── 判断问题是否无解或无界
  └── 返回最优变量值和目标值
  ↓
最终结果
  ├── 每个连续变量的取值
  ├── 最优成本或利润
  ├── 资源使用情况
  └── 求解状态
```

## 3.1 人向 LP 提供什么

人需要提供：

- 已知业务数据；
- 决策变量；
- 变量上下界；
- 线性约束；
- 线性目标函数；
- 最小化或最大化方向。

例如：

```text
已知：
原料数量
生产时间
产品利润

需要决定：
产品A生产多少
产品B生产多少

必须满足：
不能超过原料数量
不能超过机器时间

希望：
总利润最大
```

## 3.2 LP 求解器做什么

LP 求解器接收到模型后，会：

1. 分析变量和约束；
2. 找出所有满足约束的可行方案范围；
3. 在这个范围中寻找目标值最好的位置；
4. 判断是否找到最优解；
5. 返回变量值和目标函数值。

## 3.3 LP 最后返回什么

求解器通常返回：

- 求解状态；
- 每个变量的最优取值；
- 最优目标值；
- 约束的资源使用量；
- 哪些资源已经完全用完；
- 某些参数变化对结果的影响信息。

常见状态包括：

```text
OPTIMAL      找到最优解
INFEASIBLE   所有约束无法同时满足
UNBOUNDED    目标可以无限改善
UNKNOWN      暂时没有得到确定结论
```

需要特别注意：

> LP 不会自动发现现实问题中的变量、约束和目标，这些内容仍然需要由人完成建模。

# 5. 从抽象现实问题中提取 LP 模型的方法

## 5.1 什么事情需要决定

```text
什么数量需要确定？
→ 决策变量
```

LP 中的决策变量通常表示可以连续变化的数量。

常见自然语言：

| 现实表达 | 可能的 LP 变量 |
|---|---|
| 生产多少 | 产品产量 |
| 运输多少 | 运输数量 |
| 分配多少 | 资源分配量 |
| 投入多少 | 资金投入量 |
| 使用多少 | 资源使用量 |
| 混合多少 | 原料配比 |
| 购买多少 | 采购数量 |

例如：

```text
xA = 产品A的生产数量
xB = 产品B的生产数量
```

## 5.2 什么情况绝对不允许

```text
哪些限制必须满足？
→ 约束
```

常见自然语言关键词：

| 关键词 | 常见含义 |
|---|---|
| 不能超过 | 上限约束 |
| 至少需要 | 下限约束 |
| 必须等于 | 等式约束 |
| 总量有限 | 容量约束 |
| 满足需求 | 需求下限约束 |
| 保持平衡 | 流量或数量平衡约束 |
| 非负 | 变量不能小于0 |

例如：

```text
机器时间不能超过8小时
→ 产品A耗时 + 产品B耗时 ≤ 8
```

## 5.3 什么结果算更好

```text
利润更高、成本更低、运输更少、资源利用更好
→ 目标函数
```

常见关键词：

| 现实表达 | 目标 |
|---|---|
| 利润最高 | 最大化总利润 |
| 成本最低 | 最小化总成本 |
| 运输距离最短 | 最小化总运输量或成本 |
| 浪费最少 | 最小化剩余或损失 |
| 产量最大 | 最大化总产量 |

## 5.4 哪些信息在决策前已经知道

```text
已经确定、不需要算法决定的数字
→ 输入数据或模型参数
```

例如：

- 每件产品的利润；
- 每件产品需要的工时；
- 可用原料数量；
- 运输单价；
- 市场需求；
- 仓库容量；
- 能源供应量。

这些数据不是决策变量。

区别是：

```text
每件产品需要2小时
→ 已知参数

产品生产多少件
→ 决策变量
```

## 5.5 哪些信息会随着过程变化

可能发生变化的信息包括：

- 市场需求；
- 产品价格；
- 原料数量；
- 运输成本；
- 机器可用时间；
- 能源价格。

标准 LP 通常不会自己持续观察环境。

环境变化后，一般需要：

```text
获取新数据
  ↓
更新LP模型参数
  ↓
重新求解
  ↓
得到新方案
```

这可以形成滚动优化：

```text
当前状态
  ↓
求解一次LP
  ↓
执行部分决策
  ↓
获取新状态
  ↓
再次求解LP
```

## 5.6 固定提取框架

面对一个现实问题，可以依次问：

```text
已经知道哪些数据？
→ 参数

需要决定哪些数量？
→ 连续决策变量

这些数量能不能取小数？
→ 判断是否适合LP

哪些资源不能超限？
→ 上限约束

哪些需求必须满足？
→ 下限约束

哪些数量必须保持平衡？
→ 等式约束

什么结果算最好？
→ 目标函数

这些关系是不是线性的？
→ 判断是否仍属于LP
```

“线性”可以暂时理解为：

> 一个变量增加一单位，对资源消耗、成本或利润的影响保持不变。

例如：

```text
每生产1件产品A消耗2千克原料
每生产2件消耗4千克
每生产3件消耗6千克
```

这是线性关系。

如果产量增加后，单位消耗、价格或效率发生复杂变化，就可能不再是标准 LP。

# 6. 总体输入与输出

| 类型 | 内容 | 示例 |
|---|---|---|
| 原始业务输入 | 现实中的已知数据 | 原料、工时、利润、需求 |
| 建模后的输入 | 连续变量、线性约束、线性目标 | `xA`、`xB`、资源约束 |
| 求解器参数 | 控制求解过程的设置 | 时间限制、求解方法 |
| 算法内部数据 | 可行区域、基变量、方向和步长 | 求解器内部计算结果 |
| 模型输出 | 变量值和目标值 | `xA=2.67`、利润21.33 |
| 最终业务输出 | 可执行的资源方案 | A生产2.67吨，B生产2.67吨 |

## 6.1 原始业务输入

原始输入通常是：

```text
产品数据
资源数据
成本数据
利润数据
需求数据
容量数据
```

## 6.2 建模后的算法输入

建模后需要向求解器提供：

```text
变量
+ 变量范围
+ 线性约束
+ 线性目标
```

一般形式可以理解为：

```text
最大化或最小化：变量的加权总和

同时满足：
若干个变量加权总和 ≤、= 或 ≥ 某个限制
```

## 6.3 算法内部数据

求解器内部可能维护：

- 当前可行解；
- 当前目标值；
- 基变量与非基变量；
- 约束边界；
- 内点迭代方向；
- 对偶变量；
- 收敛信息。

这些内容通常由求解器处理，用户不需要自己实现。

## 6.4 最终业务输出

最终输出应该把变量值转换成现实语言。

例如：

```text
求解器输出：
xA = 2.67
xB = 2.67

业务输出：
生产2.67吨产品A
生产2.67吨产品B
预计利润约为21.33
```

# 7. 完整运行流程

```text
现实问题
  ↓
整理产品、资源、成本和利润数据
  ↓
识别需要决定的连续数量
  ↓
检查变量是否允许取小数
  ↓
检查目标和约束是否为线性关系
  ↓
创建LP变量
  ↓
添加资源、需求和平衡约束
  ↓
设置最大利润或最低成本目标
  ↓
调用LP求解器
  ↓
单纯形法或内点法求解
  ↓
得到连续变量最优值
  ↓
检查求解状态和约束
  ↓
转换为现实方案
```

# 8. 模块结构

一个实用而不过度拆分的 LP 项目可以采用：

```text
LP_Project
├── 01_Problem_Data
├── 02_Model_Builder
├── 03_Solver
├── 04_Solution
└── 05_Main
```

模型构建模块内部包含：

```text
Model_Builder
├── Variables
├── Constraints
└── Objective
```

求解器内部可能包含：

```text
Solver_Internal
├── Presolve
├── Simplex
├── Interior_Point
└── Postsolve
```

求解器内部组件通常由软件库提供，不需要用户自己编写。

# 9. 每个模块的输入、输出和构成

## 9.1 问题数据模块 Problem Data

### 作用

读取、检查并整理现实问题中的已知数据。

### 输入

- 产品信息；
- 资源信息；
- 单位利润；
- 单位成本；
- 单位资源消耗；
- 资源容量；
- 市场需求。

### 内部构成

```text
ProblemData
├── DataLoader
├── DataValidator
└── DataContainer
```

### 处理过程

1. 读取原始数据；
2. 检查缺失值；
3. 统一单位；
4. 检查数据维度；
5. 转换成模型可以使用的表格或数组。

### 输出

- 产品集合；
- 资源集合；
- 利润向量；
- 成本向量；
- 资源消耗矩阵；
- 资源容量；
- 需求上下限。

### 是否需要用户自己实现

通常需要自己实现。

求解器不知道业务数据存在哪里，也不知道每个字段代表什么。

## 9.2 模型构建模块 Model Builder

### 作用

把业务数据转换成完整的 LP 模型。

### 输入

- 结构化问题数据；
- 变量定义；
- 业务规则；
- 优化目标。

### 内部构成

```text
ModelBuilder
├── VariableBuilder
├── ConstraintBuilder
└── ObjectiveBuilder
```

### 处理过程

1. 创建 LP 模型；
2. 创建连续变量；
3. 设置变量上下界；
4. 添加线性约束；
5. 设置线性目标函数；
6. 返回模型和变量映射。

### 输出

- 完整 LP 模型；
- 变量集合；
- 业务对象与变量的映射关系。

### 是否需要用户自己实现

模型结构和业务含义需要自己实现。

创建模型、变量和约束的底层接口由求解库提供。

## 9.3 决策变量组件 Variables

### 作用

表示现实中需要确定的连续数量。

### 输入

- 业务对象；
- 变量名称；
- 最小值；
- 最大值。

### 内部构成

```text
Variables
├── ContinuousVariables
├── LowerBounds
├── UpperBounds
└── VariableIndex
```

### 处理过程

1. 找出需要决定的数量；
2. 判断变量是否允许取小数；
3. 设置变量的上下限；
4. 创建连续变量；
5. 保存变量与业务对象的对应关系。

### 输出

- 连续决策变量；
- 变量范围；
- 变量索引。

### 是否需要用户自己实现

变量的现实含义需要自己设计。

变量对象由求解库创建。

## 9.4 约束组件 Constraints

### 作用

把资源限制、需求要求和平衡关系写成线性约束。

### 输入

- 决策变量；
- 资源数据；
- 需求数据；
- 业务规则。

### 内部构成

```text
Constraints
├── CapacityConstraints
├── DemandConstraints
├── BalanceConstraints
└── BusinessConstraints
```

### 处理过程

1. 找出每条必须遵守的现实规则；
2. 确定规则涉及哪些变量；
3. 确定每个变量的影响系数；
4. 写成线性等式或不等式；
5. 将约束加入模型。

### 输出

- 容量约束；
- 需求约束；
- 平衡约束；
- 其他业务约束。

### 是否需要用户自己实现

约束的业务含义和表达方式需要自己设计。

约束对象由求解器提供。

## 9.5 目标组件 Objective

### 作用

告诉求解器哪种可行方案更好。

### 输入

- 决策变量；
- 单位成本或利润；
- 最小化或最大化方向。

### 内部构成

```text
Objective
├── ObjectiveCoefficients
├── ObjectiveExpression
└── OptimizationDirection
```

### 处理过程

1. 确定评价标准；
2. 确定每个变量对目标的贡献；
3. 形成线性加权总和；
4. 设置最大化或最小化。

### 输出

- 线性目标函数；
- 优化方向。

### 是否需要用户自己实现

目标的业务含义需要自己定义。

目标函数接口由求解库提供。

## 9.6 求解器模块 Solver

### 作用

在满足全部线性约束的连续方案中寻找最优方案。

### 输入

- 完整 LP 模型；
- 求解方法；
- 精度要求；
- 时间限制；
- 日志配置。

### 内部构成

```text
Solver
├── Presolve
├── SimplexMethod
├── InteriorPointMethod
├── ConvergenceChecker
└── Postsolve
```

### 处理过程

1. 检查模型；
2. 删除重复或无效结构；
3. 选择单纯形法或内点法；
4. 迭代改善目标值；
5. 检查是否满足约束；
6. 判断是否达到最优；
7. 恢复原变量结果。

### 输出

- 求解状态；
- 最优变量值；
- 最优目标值；
- 资源使用情况；
- 对偶信息；
- 求解统计。

### 是否需要用户自己实现

通常由求解器提供。

除非专门研究优化算法，否则不建议自己实现单纯形法或内点法。

## 9.7 解提取与验证模块 Solution

### 作用

把变量值转换成现实方案，并检查结果是否可以使用。

### 输入

- 求解状态；
- 变量值；
- 目标值；
- 原始业务数据。

### 内部构成

```text
Solution
├── SolutionExtractor
├── BusinessConverter
├── ConstraintValidator
└── ResultExporter
```

### 处理过程

1. 检查是否找到最优解；
2. 读取变量值；
3. 转换成生产、运输或分配方案；
4. 重新计算关键资源消耗；
5. 检查约束误差；
6. 输出结果表格。

### 输出

- 业务决策方案；
- 目标值；
- 资源使用报告；
- 约束验证结果。

### 是否需要用户自己实现

通常需要自己实现。

求解器返回变量和数值，但不知道用户需要什么业务报表。

## 9.8 主流程模块 Main

### 作用

按照固定顺序组织完整运行过程。

### 输入

- 数据位置；
- 模型配置；
- 求解参数。

### 内部构成

```text
Main
├── LoadData
├── BuildModel
├── SolveModel
└── ExportSolution
```

### 处理过程

```text
读取数据
→ 构建模型
→ 调用求解器
→ 提取结果
→ 验证结果
→ 输出方案
```

### 输出

- 程序运行状态；
- 最终业务方案；
- 日志和结果文件。

### 是否需要用户自己实现

通常需要自己实现，但应该保持简单，只负责组织流程。

# 10. 推荐代码结构

## 10.1 最小版本

```text
LP_Project
├── problem.py
├── solve.py
└── main.py
```

| 文件 | 作用 |
|---|---|
| `problem.py` | 保存或读取输入数据 |
| `solve.py` | 创建变量、约束和目标并求解 |
| `main.py` | 运行流程并输出结果 |

学习和小型模型使用这个结构即可。

## 10.2 完整版本

```text
LP_Project
├── data_loader.py
├── model_builder.py
├── solver.py
├── solution.py
├── validator.py
└── main.py
```

| 文件 | 作用 |
|---|---|
| `data_loader.py` | 读取和检查数据 |
| `model_builder.py` | 创建变量、约束和目标 |
| `solver.py` | 配置并调用求解器 |
| `solution.py` | 提取和转换结果 |
| `validator.py` | 独立检查约束和目标值 |
| `main.py` | 组织完整流程 |

只有当模型明显复杂时，再拆分：

```text
model/
├── variables.py
├── constraints.py
└── objective.py
```

不要因为有三个概念就强制创建三个文件。小模型放在一个 `model_builder.py` 中更清楚。

# 11. 用户需要实现什么

## 11.1 通常需要自己实现

- 理解现实问题；
- 整理输入数据；
- 找出需要决定的连续数量；
- 判断变量能否取小数；
- 创建变量；
- 提取资源限制；
- 编写线性约束；
- 定义线性目标；
- 调用求解器；
- 提取业务结果；
- 验证结果；
- 在数据变化时更新并重新求解。

## 11.2 通常由算法库或求解器提供

- 模型对象；
- 连续变量对象；
- 约束接口；
- 目标函数接口；
- 模型预处理；
- 单纯形法；
- 内点法；
- 收敛判断；
- 最优性检查；
- 对偶变量计算；
- 求解日志。

不同软件库的使用方式可能不同，但职责边界基本一致：

```text
用户负责定义正确的问题
求解器负责求解已经定义的问题
```

# 12. LP 真正帮我解决什么

## 12.1 它是在帮助我理解问题吗？

不是直接帮助。

LP 提供了一种整理问题的框架：

```text
变量
+ 线性约束
+ 线性目标
```

这个框架会迫使人说明：

- 要决定什么；
- 有哪些限制；
- 什么结果更好。

但是 LP 不会自动理解业务含义。

## 12.2 它是在帮助我建立模型吗？

部分是。

LP 告诉你可以把问题表达成连续变量、线性约束和线性目标。

但具体应该创建哪些变量、哪些约束，仍然需要人确定。

## 12.3 它是在帮助我搜索答案吗？

是。

当变量很多、约束很多时，人无法手工比较所有连续组合。LP 求解器可以高效寻找最优连续方案。

## 12.4 它是在帮助我预测结果吗？

不是。

LP 主要负责优化，不负责根据历史数据预测未来。

可以采用：

```text
机器学习
  ↓ 预测需求或价格
LP
  ↓ 根据预测值优化决策
```

## 12.5 它是在帮助我做连续决策吗？

LP 中的“连续”通常是指变量允许取小数，不等于持续与环境互动。

标准 LP 一般是：

```text
输入当前数据
→ 求解一次
→ 输出一套方案
```

如果环境持续变化，可以不断更新数据并重新求解。

## 12.6 它是在帮助我验证解是否可行吗？

可以。

给定一个候选方案后，可以检查它是否满足模型中的所有约束。

但 LP 只能检查已经写进模型的规则。遗漏的现实规则不会被自动发现。

# 13. 适用与不适用场景

| 比较适合 | 原因 |
|---|---|
| 连续生产计划 | 产量允许按吨、升等连续单位计算 |
| 原料配比 | 不同原料用量通常可以取小数 |
| 运输流量分配 | 货物流量可以连续表示 |
| 能源分配 | 功率和能量通常是连续量 |
| 投资比例分配 | 投入金额允许连续变化 |
| 资源配置 | 容量和消耗容易写成线性关系 |
| 成本最小化 | 单位成本固定时目标是线性的 |
| 利润最大化 | 单位利润固定时目标是线性的 |

| 不太适合 | 原因 |
|---|---|
| 是否选择某个项目 | 结果只能是0或1，应使用IP或MILP |
| 车辆数量 | 车辆不能取2.6辆 |
| 员工数量 | 员工通常必须是整数 |
| 任务执行顺序 | 排序逻辑不容易直接用纯LP表达 |
| 非线性效率变化 | 变量影响不再保持固定比例 |
| 复杂逻辑条件 | “如果A则B”等规则更适合MILP或CP |
| 图像和文本理解 | LP不负责提取语义 |
| 高度动态的连续交互 | 可能需要滚动优化或强化学习 |

# 14. 与相近算法比较

| 对比项 | LP | IP | MILP | CP |
|---|---|---|---|---|
| 中文名称 | 线性规划 | 整数规划 | 混合整数规划 | 约束规划 |
| 变量类型 | 连续变量 | 整数变量 | 连续和整数变量 | 整数、布尔、区间和序列变量 |
| 是否允许小数 | 允许 | 通常不允许 | 部分允许 | 由变量域决定 |
| 输入形式 | 线性变量、约束、目标 | 整数变量和线性模型 | 混合变量和线性模型 | 变量域和逻辑约束 |
| 是否需要人建模 | 需要 | 需要 | 需要 | 需要 |
| 如何求解 | 单纯形法、内点法 | 分支定界、割平面 | 分支定界、割平面 | 约束传播和搜索 |
| 是否保证可行 | 返回的解满足已建约束 | 同左 | 同左 | 同左 |
| 是否追求最优 | 通常是 | 通常是 | 通常是 | 可以求可行解或最优解 |
| 适用问题 | 连续资源分配 | 离散数量和选择 | 连续与离散混合 | 排序、调度和复杂逻辑 |

## 14.1 LP 与 IP

LP 允许：

```text
生产2.7吨产品
运输13.5吨货物
```

IP 要求：

```text
使用3辆车
选择1个仓库
安排5名员工
```

如果现实决策必须是完整个体，就不能直接接受 LP 的小数解。

## 14.2 LP 与 MILP

MILP 同时包含：

```text
连续变量 + 整数变量
```

例如：

```text
是否启动机器 → 0-1变量
机器生产多少 → 连续变量
```

这种问题不能用纯 LP 完整表达，通常使用 MILP。

## 14.3 LP 与 CP

LP 更擅长：

- 连续资源分配；
- 线性成本；
- 线性容量关系。

CP 更擅长：

- 任务顺序；
- 时间区间；
- 互斥关系；
- 复杂逻辑约束。

# 15. 可以与其他算法融合的位置

## 15.1 机器学习预测参数

```text
机器学习
  ↓ 预测需求、价格或加工时间
LP
  ↓ 优化连续资源分配
生产或运输方案
```

前一个算法输出：

- 需求预测；
- 价格预测；
- 时间预测。

LP 接收：

- 预测后的模型参数。

融合解决：

- LP 无法自己预测未来输入的问题。

## 15.2 LP 为整数优化提供理论界

```text
IP或MILP
  ↓ 暂时取消整数限制
LP松弛
  ↓ 返回理论界和小数解
分支定界
```

LP 的输出可以帮助整数求解器判断：

- 当前分支最好的理论结果；
- 是否值得继续搜索；
- 应该优先处理哪些变量。

这不是简单地把两个算法串起来，而是 IP/MILP 求解器内部的重要组成。

## 15.3 启发式算法与 LP 修复

```text
GA、PSO或其他启发式算法
  ↓ 提供候选结构或部分决策
LP
  ↓ 优化连续变量
完整候选方案
```

例如：

```text
GA决定使用哪些设施
LP决定每个设施运输多少货物
```

融合位置：

- 候选解评价；
- 连续变量优化；
- 局部修复。

## 15.4 分解算法

```text
大型LP
  ↓ 按结构拆分
主问题 + 子问题
  ↓ 交换价格或约束信息
完整方案
```

常见方法包括：

- Dantzig-Wolfe 分解；
- Benders 分解；
- 列生成；
- 拉格朗日分解。

融合目的：

- 处理变量或约束数量非常大的问题；
- 利用问题的自然结构分别求解。

## 15.5 强化学习控制重复求解

```text
环境状态
  ↓
RL选择参数或资源策略
  ↓
LP计算当前最优连续分配
  ↓
执行结果并返回新状态
```

RL 可以负责：

- 长期决策；
- 动态策略；
- 参数选择。

LP 可以负责：

- 当前时刻的可行资源分配；
- 局部精确优化。

# 16. 最小示例

## 16.1 原始问题

工厂生产产品 A 和产品 B。

已知：

| 产品 | 单位利润 | 单位工时 | 单位原料 |
|---|---:|---:|---:|
| A | 3 | 1 | 2 |
| B | 5 | 2 | 1 |

工厂有：

```text
8小时工时
8单位原料
```

希望决定两种产品分别生产多少，使利润最大。

假设产品按吨计算，因此允许生产小数数量。

## 16.2 输入数据

```text
产品A利润：3
产品B利润：5

产品A工时：1
产品B工时：2

产品A原料：2
产品B原料：1

总工时：8
总原料：8
```

## 16.3 变量

```text
xA = 产品A的生产数量
xB = 产品B的生产数量
```

变量范围：

```text
xA ≥ 0
xB ≥ 0
```

因为按吨计算，所以允许：

```text
xA = 2.67
xB = 2.67
```

## 16.4 约束

工时不能超过8：

```text
xA + 2xB ≤ 8
```

原料不能超过8：

```text
2xA + xB ≤ 8
```

产量不能为负数：

```text
xA ≥ 0
xB ≥ 0
```

## 16.5 目标

最大化总利润：

```text
maximize 3xA + 5xB
```

## 16.6 算法执行过程

求解器会检查可行范围的重要边界点。

如果只生产 A：

```text
xA = 4
xB = 0
利润 = 12
```

如果只生产 B：

```text
xA = 0
xB = 4
利润 = 20
```

如果两种产品同时生产，并且两种资源都用完：

```text
xA + 2xB = 8
2xA + xB = 8
```

可以得到：

```text
xA = 8/3 ≈ 2.67
xB = 8/3 ≈ 2.67
```

利润约为：

```text
3 × 2.67 + 5 × 2.67
≈ 21.33
```

## 16.7 输出结果

```text
产品A生产约2.67吨
产品B生产约2.67吨
最大利润约21.33
```

资源使用情况：

```text
工时使用约8小时
原料使用约8单位
```

如果产品必须按完整件生产，不能生产2.67件，那么这个问题不再适合使用纯 LP，需要改成 IP 或 MILP。

# 17. 一句话总结

> 人负责把现实问题转换成连续变量、线性约束和线性目标；LP 求解器负责在满足这些约束的连续方案中寻找最优资源分配；最终输出各变量的最优小数值和对应的成本、利润或资源使用结果。
