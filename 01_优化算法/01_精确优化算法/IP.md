# IP：整数规划

## 1. 一句话说明它是什么
> IP（Integer Programming，整数规划）是一种把“必须选择整数方案”的现实问题写成变量、约束和目标，再由求解器寻找最优方案的方法。
典型问题包括：
- 任务分配给哪个员工；
- 工序分配给哪台机器；
- 是否建设某个仓库；
- 车辆是否经过某条道路；
- 每种产品生产多少件；
- 项目选择哪些、放弃哪些。


## 3. 人和 IP 分别负责什么
```text
现实问题
  ↓
人需要完成的工作
  ├── 整理输入数据
  ├── 找出需要决定的事情
  ├── 把决定表示成整数变量
  ├── 把现实规则写成约束
  ├── 定义评价标准
  └── 检查模型是否正确
  ↓
IP求解器需要完成的工作
  ├── 分析模型
  ├── 排除不可能的方案
  ├── 搜索可行的整数方案
  ├── 比较不同方案的目标值
  ├── 尝试证明某个方案最优
  └── 返回解和求解状态
  ↓
最终结果
  ├── 选择了哪些方案
  ├── 每个整数变量的取值
  ├── 目标函数值
  └── 是否找到或证明最优解
```
### 3.1 人向 IP 提供什么
人需要向求解器提供：
- 已知数据；
- 整数或二进制变量；
- 变量允许的取值范围；
- 约束条件；
- 目标函数；
- 求解时间等参数。
### 3.2 IP 求解器做什么
求解器接收到模型后，会：
1. 检查并简化模型；
2. 暂时放松整数限制；
3. 计算当前问题的理论界限；
4. 把问题拆成若干搜索分支；
5. 排除不可能优于当前答案的分支；
6. 寻找更好的整数解；
7. 在可能时证明当前解最优。
### 3.3 IP 最后返回什么
求解器通常返回：
- 求解状态；
- 每个决策变量的值；
- 目标函数值；
- 当前最好界；
- 最优差距；
- 求解时间；
- 搜索节点数量。

## 5. 从抽象现实问题中提取 IP 模型的方法
## 5.1 什么事情需要决定
```text
什么事情需要选择、分配、安排或确定？
→ 决策变量
```
常见表达：
| 现实语言 | 可能的变量 |
|---|---|
| 是否选择 | 0-1变量 |
| 选择哪个方案 | 多个0-1变量 |
| 生产多少件 | 非负整数变量 |
| 使用多少辆车 | 整数变量 |
| 分配给哪台机器 | 机器选择变量 |
| 是否经过某条路径 | 路径选择变量 |

## 5.2 什么情况绝对不允许
```text
什么必须满足？
什么不能发生？
什么至少需要多少？
什么最多允许多少？
→ 约束
```
常见关键词：
| 现实语言 | 可能的约束 |
|---|---|
| 必须 | 等式或下限约束 |
| 不能 | 冲突或互斥约束 |
| 最多 | 上限约束 |
| 至少 | 下限约束 |
| 恰好一个 | 唯一选择约束 |
| 只有A发生才能B | 逻辑联动约束 |
| 总量不能超过容量 | 容量约束 |

## 5.3 什么结果算更好
```text
成本更低、利润更高、数量更少、时间更短
→ 目标函数
```
常见目标：
- 最小化成本；
- 最大化利润；
- 最小化车辆数量；
- 最小化延误；
- 最大化完成任务数量；
- 最小化资源消耗。

## 5.4 哪些信息已经知道
```text
决策前已经确定的数字
→ 输入数据或参数
```
例如：
- 员工数量；
- 机器数量；
- 加工时间；
- 运输成本；
- 资源容量；
- 产品利润；
- 任务需求；
- 可选方案集合。
## 5.5 哪些信息会变化
如果以下内容随时间变化：
- 新订单到达；
- 机器故障；
- 需求改变；
- 运输时间变化；
- 员工临时缺勤；
那么原来的 IP 模型可能需要：
1. 更新输入数据；
2. 固定已经执行的决定；
3. 修改变量和约束；
4. 重新调用求解器。
IP 本身通常不是持续观察环境的智能体。动态变化一般通过反复重新建模和重新求解处理。
## 5.6 固定建模模板
```text
已知什么？
→ 输入数据

需要决定什么？
→ 整数或二进制变量

什么不能违反？
→ 约束

怎样算更好？
→ 目标函数

环境变化后怎么办？
→ 更新数据并重新求解
```

## 6. 总体输入与输出
| 类型 | 内容 | 示例 |
|---|---|---|
| 原始业务输入 | 现实问题数据 | 员工、任务、成本 |
| 建模后的输入 | 变量、约束和目标 | `x[i,j]`、分配约束、最低成本 |
| 求解器参数 | 求解控制信息 | 时间限制、线程数、最优差距 |
| 算法内部数据 | 搜索节点、界、松弛解 | 当前最好整数解和理论下界 |
| 模型输出 | 变量取值和目标值 | `x[A,1]=1`、成本11 |
| 业务输出 | 可执行的现实方案 | A交给员工1 |
需要注意：
> 求解器通常只认识变量和数字，不认识“员工A工作很熟练”这样的模糊表达。
这类现实信息需要先转换成：
- 成本；
- 时间；
- 能力参数；
- 可行或不可行规则。

## 7. 完整运行流程
```text
现实问题
  ↓
整理问题数据
  ↓
识别需要决定的内容
  ↓
创建整数或二进制变量
  ↓
添加现实规则对应的约束
  ↓
定义成本、利润或时间目标
  ↓
生成IP模型
  ↓
调用IP求解器
  ↓
求解器执行松弛、分支、剪枝和割平面
  ↓
得到整数候选解
  ↓
检查求解状态和约束
  ↓
转换为现实方案
```

## 8. 模块结构
一个实用而不过度拆分的 IP 项目可以分为：
```text
IP_Project
├── 01_Problem_Data
├── 02_Model_Builder
├── 03_Solver
├── 04_Solution
└── 05_Main
```
其中模型构建模块内部包含：
```text
Model_Builder
├── Variables
├── Constraints
└── Objective
```
求解器内部通常包含：
```text
Solver_Internal
├── Presolve
├── Relaxation
├── Branching
├── Bounding
├── Cutting
└── Heuristics
```
求解器内部模块通常不需要用户自己实现。

## 9. 每个模块的输入、输出和构成
## 9.1 问题数据模块 Problem Data
### 作用
读取、清洗并保存现实问题的已知信息。
### 输入
- 原始文件；
- 数据库记录；
- 人工配置；
- 任务、资源、成本和容量信息。
### 内部构成
```text
ProblemData
├── DataLoader
├── DataValidator
└── DataContainer
```

### 处理过程

1. 读取原始数据；
2. 检查数据是否缺失；
3. 统一编号和单位；
4. 转换成模型容易使用的结构；
5. 保存任务、资源和成本参数。

### 输出
- 任务集合；
- 资源集合；
- 成本矩阵；
- 容量参数；
- 允许关系；
- 其他模型参数。

### 是否需要用户自己实现
通常需要自己实现，因为求解器不知道业务数据的格式和含义。

---
## 9.2 模型构建模块 Model Builder
### 作用
把业务问题转换成 IP 模型。
### 输入
- 结构化问题数据；
- 建模规则；
- 优化目标。

### 内部构成
```text
ModelBuilder
├── VariableBuilder
├── ConstraintBuilder
└── ObjectiveBuilder
```

### 处理过程
1. 创建模型；
2. 创建整数和二进制变量；
3. 设置变量上下界；
4. 添加约束；
5. 添加目标函数；
6. 返回完整模型。

### 输出
- 完整 IP 模型；
- 变量索引或变量映射表。

### 是否需要用户自己实现
建模逻辑通常需要自己实现。
创建变量和添加约束的底层接口由软件库提供。

---
## 9.3 决策变量组件 Variables
### 作用
表示现实中需要确定的决策。
### 输入
- 业务对象；
- 变量名称；
- 变量类型；
- 变量上下界。
### 内部构成
```text
Variables
├── BinaryVariables
├── IntegerVariables
└── VariableIndex
```
### 处理过程
1. 找到每个需要决定的业务关系；
2. 为其创建变量；
3. 指定变量只能取整数；
4. 保存变量与业务对象的对应关系。
### 输出
- 二进制变量；
- 一般整数变量；
- 业务对象到变量的映射。

### 是否需要用户自己实现
变量含义和创建规则需要自己设计。
变量对象本身由求解库创建。

---
## 9.4 约束组件 Constraints
### 作用
把现实中的必须、不能、至少和至多转换成数学限制。
### 输入
- 决策变量；
- 业务规则；
- 容量和需求参数。
### 内部构成
```text
Constraints
├── AssignmentConstraints
├── CapacityConstraints
├── LinkingConstraints
└── BusinessConstraints
```
### 处理过程
1. 找出每条现实规则；
2. 确定它涉及哪些变量；
3. 将规则转换成等式或不等式；
4. 将约束加入模型。

### 输出
- 加入模型的全部约束；
- 可选的约束名称和索引。

### 是否需要用户自己实现
约束含义和表达方式通常需要自己实现。
约束存储和处理由求解器完成。

---
## 9.5 目标组件 Objective
### 作用
告诉求解器哪种可行方案更好。
### 输入
- 决策变量；
- 成本、利润、时间等参数；
- 最小化或最大化方向。

### 内部构成
```text
Objective
├── ObjectiveCoefficients
├── ObjectiveExpression
└── OptimizationDirection
```

### 处理过程
1. 确定评价标准；
2. 计算每个变量对目标的影响；
3. 形成总成本或总利润表达式；
4. 设置最小化或最大化。

### 输出
- 目标函数；
- 优化方向。

### 是否需要用户自己实现
目标含义和计算方式需要自己设计。
目标函数接口由求解库提供。

---
## 9.6 求解器模块 Solver
### 作用
在满足约束的整数方案中寻找最好方案。
### 输入
- 完整 IP 模型；
- 时间限制；
- 线程数量；
- 最优差距；
- 可选初始解。

### 内部构成
```text
Solver
├── Presolve
├── LPRelaxation
├── BranchAndBound
├── CuttingPlanes
├── PrimalHeuristics
└── SolutionPool
```

### 处理过程
1. 预处理并简化模型；
2. 暂时允许整数变量取小数，求解松弛问题；
3. 使用松弛结果计算理论界；
4. 对非整数变量进行分支；
5. 形成新的子问题；
6. 排除不可能更优的分支；
7. 添加割平面缩小搜索区域；
8. 保存更好的整数解；
9. 达到停止条件后返回结果。

### 输出
- 求解状态；
- 最优或当前最好整数解；
- 目标函数值；
- 最优界；
- 最优差距；
- 求解统计信息。

### 是否需要用户自己实现
通常由 Gurobi、CPLEX、SCIP、OR-Tools 等求解器提供。
除非研究 IP 求解算法，否则不建议自己实现分支定界和割平面。

---
## 9.7 解提取与验证模块 Solution
### 作用
把变量值转换成现实方案，并检查结果是否合理。

### 输入
- 求解状态；
- 变量取值；
- 原始业务数据；
- 目标函数值。

### 内部构成
```text
Solution
├── SolutionExtractor
├── BusinessConverter
├── ConstraintValidator
└── ResultExporter
```
### 处理过程
1. 检查求解器是否找到解；
2. 读取整数变量的值；
3. 将变量还原为任务分配或生产计划；
4. 重新计算目标值；
5. 检查关键业务约束；
6. 输出表格、文件或可视化数据。

### 输出
- 现实决策方案；
- 目标值；
- 验证结果；
- 结果文件或报表。
### 是否需要用户自己实现
通常需要自己实现，因为求解器只返回变量值，不知道业务输出需要什么形式。
---

## 9.8 主流程模块 Main
### 作用
按照固定顺序组织整个求解过程。
### 输入
- 数据文件路径；
- 模型配置；
- 求解参数。

### 内部构成
```text
Main
├── LoadData
├── BuildModel
├── SolveModel
└── ExportSolution
```
### 处理过程
```text
读取数据
→ 构建模型
→ 调用求解器
→ 提取结果
→ 验证结果
→ 输出结果
```
### 输出
- 最终运行状态；
- 业务方案；
- 日志和统计信息。

### 是否需要用户自己实现
通常需要自己实现，但内容应该很短，只负责组织流程。

## 10. 推荐代码结构
## 10.1 最小版本
```text
IP_Project
├── problem.py
├── solve.py
└── main.py
```
| 文件 | 作用 |
|---|---|
| `problem.py` | 保存或读取问题数据 |
| `solve.py` | 创建变量、约束、目标并调用求解器 |
| `main.py` | 运行整个流程并输出结果 |
小型学习项目使用这个结构就足够，不需要过度拆分。
## 10.2 完整版本
```text
IP_Project
├── data_loader.py
├── model_builder.py
├── solver.py
├── solution.py
├── validator.py
└── main.py
```
| 文件 | 作用 |
|---|---|
| `data_loader.py` | 读取和检查数据 |
| `model_builder.py` | 创建变量、约束和目标 |
| `solver.py` | 设置求解参数并调用求解器 |
| `solution.py` | 提取并转换结果 |
| `validator.py` | 独立检查约束和目标值 |
| `main.py` | 组织执行顺序 |
只有当模型明显变大时，才进一步拆分：
```text
model/
├── variables.py
├── constraints.py
└── objective.py
```

## 12. IP 真正帮我解决什么
### 12.1 它是在帮助我理解问题吗？
不是直接帮助。
IP 提供了一套建模框架，迫使建模者明确：
- 什么需要决定；
- 什么必须满足；
- 什么需要优化。
这个过程有助于人整理问题，但 IP 不会代替人理解业务。
### 12.2 它是在帮助我建立模型吗？
部分是。
IP 告诉你模型应该包含：
```text
整数变量 + 约束 + 目标
```
但具体变量和约束是什么，需要由人决定。
建模软件可以帮助你把这些内容写进计算机，但不会保证业务模型正确。
### 12.3 它是在帮助我搜索答案吗？
是，这是 IP 求解器的核心作用。
当合法组合数量非常大时，求解器通过分支、界和剪枝寻找较好或最优的整数方案。
### 12.4 它是在帮助我预测结果吗？
通常不是。
IP 主要进行优化决策，不负责从历史数据预测未来。
如果加工时间、需求或价格未知，可以先用机器学习预测，再把预测结果输入 IP。
### 12.5 它是在帮助我做连续决策吗？
通常不是直接完成。
标准 IP 更像：
```text
给定当前数据
→ 求解一次
→ 返回一套方案
```
如果环境持续变化，可以循环执行：
```text
获取新状态
→ 更新IP模型
→ 重新求解
→ 执行部分决策
→ 获取下一状态
```
这种方式称为滚动优化或重复优化。
### 12.6 它是在帮助我验证解是否可行吗？
可以。
如果把一个候选方案固定到变量中，求解器可以检查它是否满足模型中的约束。
但它只能验证已经写进模型的约束。
如果漏写了某条现实规则，求解器不会自动发现。

## 13. 适用与不适用场景
| 比较适合 | 原因 |
|---|---|
| 任务分配 | 选择关系可以用0-1变量表示 |
| 设施选址 | 是否建设可以表示为二进制变量 |
| 生产数量决策 | 产品数量天然是整数 |
| 车辆路径选择 | 是否使用边可以表示为0-1变量 |
| 项目组合选择 | 每个项目可以选择或不选择 |
| 资源配置 | 容量、需求和成本容易写成约束 |
| 中小规模精确优化 | 求解器可以寻找并证明最优解 |
| 需要明确可行性的决策 | 约束可以严格排除不合法方案 |

| 不太适合 | 原因 |
|---|---|
| 现实规则无法明确表达 | 无法形成可靠约束 |
| 输入数据高度不确定 | 单次静态模型可能很快失效 |
| 超大规模且要求瞬间响应 | 精确搜索可能耗时较长 |
| 图像和文本直接理解 | IP 不负责提取语义特征 |
| 主要任务是预测 | 应优先使用统计或机器学习方法 |
| 奖励延迟的连续交互决策 | 强化学习可能更自然 |
| 强非线性且难以线性化的问题 | 标准线性 IP 表达困难 |

## 14. 与相近方法比较
| 对比项 | IP | LP | MILP | CP |
|---|---|---|---|---|
| 中文名称 | 整数规划 | 线性规划 | 混合整数规划 | 约束规划 |
| 变量类型 | 全部或核心变量为整数 | 连续变量 | 同时有整数和连续变量 | 整数、布尔、区间、序列等 |
| 输入形式 | 变量、线性约束、线性目标 | 连续变量和线性模型 | 混合变量和线性模型 | 变量域和逻辑约束 |
| 是否需要人建模 | 需要 | 需要 | 需要 | 需要 |
| 核心求解方式 | 分支定界、割平面 | 单纯形法、内点法等 | 分支定界、割平面 | 约束传播和搜索 |
| 是否保证变量为整数 | 是 | 否 | 指定的变量是 | 根据变量域决定 |
| 是否保证可行 | 只有找到满足全部约束的解才可行 | 同左 | 同左 | 同左 |
| 是否追求最优 | 通常是 | 通常是 | 通常是 | 可以只找可行解，也可以优化 |
| 适合问题 | 离散选择和数量决策 | 连续资源分配 | 离散与连续混合问题 | 排序、调度和复杂逻辑 |
| 最优性证明 | 求解器可能提供 | 通常可以 | 求解器可能提供 | 取决于求解器和问题 |

### 14.1 IP 与 LP
如果变量允许取：
```text
2.3、5.7、10.25
```
通常属于 LP。
如果变量必须取：
```text
0、1、2、3
```
通常属于 IP。
### 14.2 IP 与 MILP
如果模型中的变量全部要求为整数，可以称为纯整数规划。
如果模型同时包含：
```text
整数变量 + 连续变量
```
则属于 MILP。
实际工程中，MILP 比纯 IP 更常见。
### 14.3 IP 与 CP
IP 更擅长表达：
- 数量；
- 成本；
- 容量；
- 线性资源关系。

CP 更擅长表达：
- 时间区间；
- 任务顺序；
- 互斥关系；
- 复杂逻辑。

两者都需要人定义变量和约束。

## 15. 可以与其他算法融合的位置
## 15.1 启发式算法提供初始解
```text
GA、贪心或局部搜索
  ↓ 提供一个可行候选方案
IP求解器
  ↓ 继续改进并计算最优界
更好的方案或最优方案
```

融合目的：
- 让 IP 更早得到高质量可行解；
- 帮助剪掉更多搜索分支；
- 缩短找到好答案的时间。

融合位置：
- 初始解模块；
- 热启动模块。

## 15.2 IP 修复启发式算法产生的解
```text
GA或RL
  ↓ 产生可能违反约束的候选解
IP
  ↓ 修复分配和容量冲突
可行方案
```
融合目的：
- 保留启发式算法的搜索能力；
- 使用 IP 保证关键约束被满足。

融合位置：
- 候选解修复；
- 局部精确优化。

## 15.3 机器学习预测参数
```text
机器学习
  ↓ 预测需求、加工时间或成本
IP
  ↓ 根据预测数据求最优决策
生产或调度方案
```
融合目的：
- 机器学习负责预测未知数据；
- IP 负责在预测结果基础上优化决策。

## 15.4 强化学习选择求解策略
```text
IP当前求解状态
  ↓
RL选择分支变量、割或启发式策略
  ↓
IP继续搜索
```
融合目的：
- 让求解器根据不同问题自适应选择搜索策略。
融合位置：
- 分支变量选择；
- 节点选择；
- 启发式策略选择；
- 求解参数控制。

## 15.5 分解算法处理大规模问题
```text
原始大型IP
  ↓ 分解
主问题 + 多个子问题
  ↓ 分别求解并交换信息
完整方案
```
常见思想包括：
- Benders 分解；
- Dantzig-Wolfe 分解；
- 拉格朗日松弛；
- 列生成。

融合目的：
- 避免一次性求解整个超大模型；
- 利用问题结构降低难度。

## 16. 最小示例
## 16.1 原始问题
有两个项目：

| 项目 | 成本 | 收益 |
|---|---:|---:|
| A | 4 | 7 |
| B | 3 | 5 |
当前预算为4。
需要决定选择哪些项目，使总收益最大。
## 16.2 输入数据
```text
项目A：成本4，收益7
项目B：成本3，收益5
预算：4
```

## 16.3 变量
```text
xA = 1：选择项目A
xA = 0：不选择项目A

xB = 1：选择项目B
xB = 0：不选择项目B
```

## 16.4 约束
总成本不能超过预算：
```text
4 × xA + 3 × xB ≤ 4
```

变量只能取0或1：
```text
xA, xB ∈ {0,1}
```

## 16.5 目标
最大化总收益：

```text
maximize 7 × xA + 5 × xB
```

## 16.6 手工检查全部方案
| `xA` | `xB` | 总成本 | 总收益 | 是否可行 |
|---:|---:|---:|---:|---|
| 0 | 0 | 0 | 0 | 是 |
| 1 | 0 | 4 | 7 | 是 |
| 0 | 1 | 3 | 5 | 是 |
| 1 | 1 | 7 | 12 | 否，超过预算 |

## 16.7 输出结果
```text
xA = 1
xB = 0
最大收益 = 7
```

现实含义：
```text
选择项目A
不选择项目B
预算使用4
获得收益7
```

## 17. 一句话总结
> 人负责把现实问题转换成整数变量、约束和目标；IP 求解器负责在大量整数方案中排除不合法选择并寻找最优选择；最终输出满足模型约束的整数决策方案和目标值。
